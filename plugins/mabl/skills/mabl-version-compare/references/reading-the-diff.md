# Reading the structured diff

Mechanics for the normalize-before-you-count step of `SKILL.md`. Read that first — this is
the detail behind the classification, not a separate workflow.

Both surfaces run the same engine and emit the same object: the CLI prints it, the MCP compare tool
returns it as `structuredContent`. The recipes here assume it is in a file, which is the CLI's form;
from the MCP tool it arrives parsed, so read the same paths directly.

## What the payload will not tell you correctly

Read the object for its shape. These are the places where reading it leads somewhere wrong.

| | |
|---|---|
| `to` on an `unchanged` entry | **absent entirely**, not null — the step is identical so it is carried once, in `from`. The side that always exists is `.to // .from`. Reach for `.to` and every unchanged step vanishes silently. |
| `stepNumber` | a position **within its own version**: the target's for present/added/changed steps, the source's for removed ones. Not a stable identifier, and the two sides do not line up. |
| `id` | present only when the step has one. Steps written by hand through the step-edit tools carry none; agent-authored steps do. Where ids are absent, pairing degrades to a body comparison, which cannot tell a move from a delete-plus-identical-add. |
| `disabled` | present **only when true**. An enabled step has no `disabled` key, so treat absent as enabled rather than looking for `false`. |
| `description`, `annotation` | server-rendered, regenerated by the platform, and able to contradict the body they describe. The body is authoritative. |
| `condition`, `extract` | **siblings** of `target`, not children. That is the only reason stripping the locator leaves a requirement behind to compare. |
| `summary` | counts **steps**, not assertions. |
| `EvaluateFlow` | the whole descriptor is `{actionCode, description, flow, id}`, plus `config` when the caller set one. On a reference to a saved flow, `flow` carries `invariant_id` alone. There is **no flow version anywhere on it** — the step names a flow, and which version applies is resolved on read, not stored. |
| `flow` without an `invariant_id` | the schema's other shape is an inline flow definition, `{name, parameters}`, whose steps ride on the `EvaluateFlow` step itself. None were seen here, but an enumeration keyed on `invariant_id` drops them without a word. Their steps are already in the diff — classify them in place. |
| `config` on an `EvaluateFlow` | absent when nothing was configured. Holds `parameters`, `iterations`, and `role`; `role: "teardown"` runs the flow at the end of the test even after an earlier step failed, and defaults to `normal`. Absent against an explicit `iteration_type: "none"` or `role: "normal"` is churn; absent against anything else is a change. |

## jq recipes

### Assertion count per type, both sides

Assertions are the types starting with `Assert`, plus `AccessibilityCheck` where the question is
"what does this test verify". `WaitUntil`, `If` and `ElseIf` carry the same condition shape and are
**not** assertions — counting "has a condition" over-counts every wait in the test.

```bash
# target side: steps present in the target version
jq '[.steps[]
     | select(.operation == "added" or .operation == "changed" or .operation == "unchanged")
     | (.to // .from) | to_entries[0].key
     | select(startswith("Assert") or . == "AccessibilityCheck")]
    | group_by(.) | map({type: .[0], count: length})' "$DIFF"

# source side: steps present in the source version
jq '[.steps[]
     | select(.operation == "removed" or .operation == "changed" or .operation == "unchanged")
     | .from | to_entries[0].key
     | select(startswith("Assert") or . == "AccessibilityCheck")]
    | group_by(.) | map({type: .[0], count: length})' "$DIFF"
```

Report both columns and the net. A net of zero with a changed type breakdown is the interesting
case, and a bare total hides it.

An `AccessibilityCheck` **can** carry assertions and does not always; without them it still produces
non-functional accessibility data. So say which question the count answers — what the test verifies,
or what gates the run — rather than treating the type name as the answer.

### Reconciling the add/remove axis against the counts

Exclude moved pairs before counting — a move is one relocation, not a deletion plus an addition.

```bash
jq '
  [ .steps[] | select(.operation == "added")
    | (.to   | to_entries[0].value.id) | select(. != null) ] as $a
  | [ .steps[] | select(.operation == "removed")
      | (.from | to_entries[0].value.id) | select(. != null) ] as $r
  | ($a - ($a - $r)) as $moved
  | { moved: ($moved | length),
      added_excl_moved:   ([ $a[] | . as $x | select(($moved | index($x)) == null) ] | length),
      removed_excl_moved: ([ $r[] | . as $x | select(($moved | index($x)) == null) ] | length) }
' "$DIFF"
```

Bind `$x` before the lookup. `$moved | index(.)` rebinds `.` to `$moved`, the filter drops
everything, and both totals come back `0`.

**Reconcile in aggregate, not per type.** `added == net + removed` holds across all assertions. It
does **not** hold for a single type, because a `changed` step can change type — an
`AssertStartsWith` becoming an `AssertContains` moves one count between two types while appearing in
neither `added` nor `removed`. Applied per type on a correct diff that contains one type change, the
check reports two false alarms. Either reconcile the aggregate, or add the type-migration term
before comparing.

### Is this `changed` step actually an edit?

`description` and `annotation` are regenerated by the platform, so a step can be `changed` with no
behavioural difference. Strip both sides and compare the remainder — comparing whole objects also
catches a key that **appears** on the target side, which a walk over the source's keys would miss.

```bash
jq '[.steps[] | select(.operation == "changed")
     | { step: .stepNumber,
         type: (.to | to_entries[0].key),
         churn_only: (
           ((.from | to_entries[0].value) | del(.description, .annotation))
           == ((.to | to_entries[0].value) | del(.description, .annotation)) ) }]
    | { churn: [.[] | select(.churn_only)] | length,
        real:  [.[] | select(.churn_only | not)] | length,
        detail: . }' "$DIFF"
```

`churn` is reported separately, never folded into "steps changed". When `real` is 0, the version
changed no behaviour — say that outright.

### Pairing a removed step: evidence, not a verdict

`removed` means *left this position*. This emits the facts the ladder in `SKILL.md` consumes; the
ladder decides, so the order lives in one place.

Candidate matches are emitted as **lists**, not booleans. Two identically-bodied removed steps can
both match one added step, and a boolean would let the second one silently claim the same partner.

```bash
jq '
  def residue: del(.id, .description, .annotation, .target, .find);
  def discriminating:
    ([ .condition.comparatorValue, .condition.userPrompt, .value, .name,
       .generator.pattern, .extract.attributeName ]
     | map(select(. != null)) | length > 0)
    or ((.condition.conditionType // "presence") != "presence");

  ( [ .steps[] | select(.operation != "added")   | (.from | to_entries[0].key) ]
    | group_by(.) | map({ (.[0]): length }) | add ) as $src
  | ( [ .steps[] | select(.operation != "removed") | ((.to // .from) | to_entries[0].key) ]
      | group_by(.) | map({ (.[0]): length }) | add ) as $tgt
  | ( [ .steps[] | select(.operation != "removed")
        | (.to // .from) | to_entries[0] | select(.key == "EvaluateFlow")
        | .value.flow.invariant_id ] | map(select(. != null)) | unique ) as $tgtflows
  | [ .steps[] | select(.operation == "added")
      | (.to | to_entries[0]) as $e
      | { step: .stepNumber, type: $e.key, id: $e.value.id,
          flow: $e.value.flow.invariant_id, cfg: $e.value.config,
          body: ($e.value | del(.id, .description, .annotation)),
          res:  ($e.value | residue) } ] as $added
  | [ .steps[] | select(.operation == "removed")
      | (.from | to_entries[0]) as $e
      | { step: .stepNumber, type: $e.key, id: $e.value.id } as $base
      | ($e.value | del(.id, .description, .annotation)) as $body
      | ($e.value | residue) as $res
      | ($e.value | discriminating) as $disc
      | ($e.value.flow.invariant_id) as $fid
      | ($e.value.config) as $cfg
      | ($added | map(select(.type == $base.type))) as $same
      | ($added | map(select($fid != null and .flow == $fid))) as $sameflow
      | $base + {
          matched_by_id:   [ $added[] | select($base.id != null and .id == $base.id) | .step ],
          matched_by_body: [ $added[] | select(.body == $body) | .step ],
          matched_by_flow_same_config: [ $sameflow[] | select(.cfg == $cfg) | .step ],
          matched_by_flow_diff_config: [ $sameflow[] | select(.cfg != $cfg) | .step ],
          flow_absent_from_target: ($fid != null and (($tgtflows | index($fid)) == null)),
          residue_discriminating: $disc,
          matched_by_residue: [ $same[] | select(.res == $res) | .step ],
          same_type_added: [ $same[] | .step ],
          src_count: ($src[$base.type] // 0),
          tgt_count: ($tgt[$base.type] // 0) } ]
' "$DIFF"
```

The `flow.invariant_id` match is split on `config` because the ladder splits on
it. An `EvaluateFlow` written through the step-edit tools carries no `id`, so a
`config` edit arrives as a removal plus an addition sharing one `invariant_id`,
and a single `matched_by_flow` list cannot tell that apart from an id-assignment
migration. `flow_absent_from_target` is what separates a flow the test stopped
calling from one it still calls.

`residue_discriminating` is the guard, and it is not optional. `residue` strips `target` and `find`,
so a step whose whole meaning is its target strips to `{actionCode}` alone: every `Hover` matches
every other `Hover`, every `Click` every other `Click`, and a bare presence wait matches every other
presence wait in the test. Without the guard, a residue match asserts that a step survived when the
data cannot support it.

**Do not add `condition` or `extract` to the strip list.** They are siblings of `target`, not
children, which is the only reason a residue match discriminates at all — real deletions differ on
`condition.comparatorValue` and `extract.attributeName`. Folding either into the strip, on the
reasonable-sounding grounds that extraction is part of locating a value, makes the residue match
vacuous for every assertion at once.

More than one entry in a `matched_by_*` list is an ambiguity, not a match. Say so rather than picking
the first.

### Was it extracted into a reusable flow?

The one resolution that needs a second call, and the reason a removal cannot be settled from the
diff alone. Any target-side `EvaluateFlow` — `added`, or `changed` into one — is a candidate:

```bash
jq -c '[.steps[]
        | select(.operation == "added" or .operation == "changed")
        | select((.to | to_entries[0].key) == "EvaluateFlow")
        | { step: .stepNumber, op: .operation,
            was: (.from | if . == null then null else to_entries[0].key end),
            flow: (.to | to_entries[0].value.flow.invariant_id) }]' "$DIFF"
```

A hit with `op: "changed"` and `was: "StepGroup"` is the classic extraction signature — and that
shape has **no added steps at all**, so every removal will look unmatched until you read the flow.

For each flow id, two calls, the branch first:

```
list_mabl_flow_versions({ flowId: "<*-f>" })        # take created_on_branch
get_mabl_flow_steps({ flow_id: "<*-f>", branch: "<that branch>" })
```

**Pass the branch.** `get_mabl_flow_steps` accepts only a bare invariant id and defaults to master,
so a flow created on an agent-edit branch reads back `step_count: 0` — indistinguishable from the
steps having been deleted into an empty flow. Nothing in that response says "wrong branch", so this
is the one check here that does not fail safe.

```bash
# $FLOW = the get_mabl_flow_steps response saved to a file
jq -n --slurpfile d "$DIFF" --slurpfile f "$FLOW" '
  [ $f[0].steps[].id ] as $inflow
  | [ $d[0].steps[] | select(.operation == "removed")
      | { step: .stepNumber,
          type: (.from | to_entries[0].key),
          id:   (.from | to_entries[0].value.id) } ]
  | map(. as $r | $r + { in_flow:
        (($r.id != null) and (($inflow | index($r.id)) != null)) })'
```

Ids survive extraction, so this match is exact. A removal with no id, or one absent from the flow, is
either a genuine deletion or unresolvable — say which, and never report an unresolved removal as a
deletion.

### Enumerating the flows on each side

Step 4 of `SKILL.md` starts here. The two sides are read the same way as everywhere else:
source is everything that is not `added`, taken from `.from`; target is everything that is not
`removed`, taken from `.to // .from`.

```bash
jq -c '
  { source: ( [ .steps[] | select(.operation != "added")
                | .from | to_entries[0] | select(.key == "EvaluateFlow")
                | .value.flow.invariant_id ] | map(select(. != null)) | unique ),
    target: ( [ .steps[] | select(.operation != "removed")
                | (.to // .from) | to_entries[0] | select(.key == "EvaluateFlow")
                | .value.flow.invariant_id ] | map(select(. != null)) | unique ) }
  | . + { both:        (.source - (.source - .target)),
          source_only: (.source - .target),
          target_only: (.target - .source) }
' "$DIFF"
```

`both` gets a version-resolved diff. `source_only` is a flow the test stopped calling,
`target_only` one it started calling; both are functional changes to the test, and both want
the flow's contents reported so the caller can see what coverage moved.

`map(select(. != null))` is where an inline flow definition disappears: it has `flow.name`
rather than `flow.invariant_id`, so it enumerates as null and gets filtered. Count them
separately if you need to know they were there — its steps are on the `EvaluateFlow` step
itself and are classified in place, not fetched.

Selecting on `.key` is what keeps an extraction out of the source list: when a `StepGroup`
becomes an `EvaluateFlow`, the `changed` entry's `.from` is still keyed `StepGroup`, so it is
correctly absent from `source` and present in `target`.

The call sites, with the step numbers to attribute findings to and the `config` that drives
each one:

```bash
jq -c '[ .steps[]
         | . as $s
         | (($s.to // $s.from) | to_entries[0]) as $e
         | select($e.key == "EvaluateFlow")
         | { step: $s.stepNumber, op: $s.operation,
             flow: $e.value.flow.invariant_id,
             desc: $e.value.description,
             config: $e.value.config } ]' "$DIFF"
```

Bind `$s` before descending. `.stepNumber` is a sibling of `.to` / `.from`, so reaching for it
after piping into the descriptor returns null for every row.

### Resolving which flow version each side used

Nothing records it, so this is an inference and the report says so. Take the newest flow
version created at or before the test version's `created_time`; both lists are Unix epoch
milliseconds on the same clock.

```bash
# $TVERS = list_mabl_test_versions response saved to a file
# $FVERS = list_mabl_flow_versions response saved to a file, unfiltered by branch
jq -n --slurpfile t "$TVERS" --slurpfile f "$FVERS" --argjson n 72 '
  ($t[0].versions[] | select(.version == $n) | .created_time) as $at
  | [ $f[0].versions[] | select(.created_time <= $at) ]
  | if length == 0
    then { test_version: $n, resolved: null,
           note: "no flow version was created at or before this test version" }
    else (max_by(.created_time))
         | { test_version: $n, resolved: .version, created_time,
             created_on_branch: (.created_on_branch // "unrecorded") }
    end'
```

Three things this shape is deliberate about:

- **`max_by(.created_time)`, not `.[0]`.** The list is documented newest-first; deriving the
  answer from the timestamps instead of the ordering costs nothing and cannot silently invert.
- **`.created_on_branch // "unrecorded"`.** Versions predating branching carry only `version`,
  `is_latest` and `created_time`. Reporting `unrecorded` keeps them; filtering the list with
  `list_mabl_flow_versions({ branch: "master" })` drops them along with the other-branch
  versions it was asked to drop — one flow here went from 11 versions to 4 — and nothing in the
  response says anything was dropped.
- **The empty case is real** and is reported as unresolved, not as version 0. Run both sides,
  and when they resolve to the same version say so rather than diffing a version against
  itself, which `compare` rejects on identical argument strings anyway.

Carry the resolved `created_on_branch` into the report. A test version created on one branch
resolving to a flow version created on another is worth stating: those two never coexisted on
a single branch.

### Reconstructing a flow's steps at one version

`get_mabl_flow_steps` rejects `:N` outright — `<*-f>:3` errors with *"contains a variant suffix
(\":N\"). Pass the bare invariant id"* — and otherwise returns the latest on a branch. So a
specific version is read by diffing it against its predecessor and keeping the target side:

```bash
mabl flows compare "$FLOW:$((N-1))" "$FLOW:$N" --output json > "$FLOWDIFF"

jq -c '[ .steps[] | select(.operation != "removed")
         | { step: .stepNumber,
             type: ((.to // .from) | to_entries[0].key),
             body: ((.to // .from) | to_entries[0].value) } ]' "$FLOWDIFF"
```

At `N == 0` there is no predecessor. Fall back to `get_mabl_flow_steps` and say the steps shown
are the flow's latest, not the version resolved for this side.

The `version_token` on a `get_mabl_flow_steps` response (e.g.
`"a9e5288824406d77:f12582d37a7110b4--gzip"`) is an opaque string. It is not a version number,
and nothing in that response maps it to one — the response carries no version field at all.

### Whether the test itself is enabled

Not in this diff at all, and one of the most common real "edits":

```bash
mabl tests list -o json --limit 2000 | jq -r '.[] | select(.id == "<test-id>-j") | {id, name, enabled, last_updated_time, last_updated_by_user}'
```

That payload carries `created_by_user` and `last_updated_by_user` as resolved `{id, name, email}`
objects — the only reliable attribution route, and it names the test record's last editor rather
than the author of any one version.

## Edge cases that make a naive count wrong

| Trap | What actually happens |
|---|---|
| A moved step read as a deletion | rendered as `removed` + `added`, the way the web app's Compare tab renders it; pair by id first |
| A moved step counted on the add/remove axis | same pair; exclude moved pairs before counting or the added total reads one too high |
| The axis reconciled per type | a `changed` step can change type, moving a count between two types while appearing in neither `added` nor `removed`. Reconcile the aggregate |
| A residue match trusted without the guard | `Hover`/`Click` strip to `{actionCode}` and every presence wait strips alike, so any same-type pair looks retargeted |
| A flat type count read as "something replaced it" | a `changed` step can morph *into* that type, so the count holds with nothing added. Ask whether anything of the type was **added**, not only whether the count dropped |
| One added step claimed by two removals | identically-bodied removals both match it; more than one candidate is an ambiguity, not a match |
| `unchanged` entries missing `to` | the step is identical, carried once in `from`; `.to // .from` handles it |
| `stepNumber` compared across sides | numbered per version; a step at 7 in the source is not the step at 7 in the target |
| `disabled: false` looked for | the key exists only when true |
| Waits counted as assertions | `WaitUntil` / `If` / `ElseIf` share the condition shape; count by the type key |
| An `Assert*` that became a `WaitUntil` | a wait proves nothing, so this is a check removed while the step count stays intact |
| Step groups expanded | flattened — a group header carries no nested `steps`, so grouped steps appear as their own entries |
| A bare `<id>` assumed to mean "latest on master" | a bare reference resolves to the **global latest version**, which may have been created on a branch. Name both versions as `<id>:<N>` — a versioned reference is branch-independent on both lanes |
| `description` or `annotation` read as the step | both are server-rendered commentary and drift from the body. Strip them before comparing, and classify from `condition` / `extract` / `target` / `url` / `text` / `generator` |
| An id mismatch read as a deletion | an id match proves a move; a mismatch proves nothing. Compare bodies with `id` excluded — a regenerated id is not a deleted step |
| `EvaluateFlow` remove+add read as a dropped flow | an id-assignment migration nulls the removed side's id AND changes the description, so both id and descriptor pairing fail. Pair on `flow.invariant_id` + `stepNumber` |
| `EvaluateFlow` remove+add read as an id migration | the reverse error. A migration shares one `flow.invariant_id` across both sides; **different** invariant ids are one flow swapped for another, which is a functional change to the test |
| An `EvaluateFlow` `config` edit read as an id migration | a hand-authored `EvaluateFlow` carries no `id`, so adding `config` to one arrives as a remove plus an add sharing a single `flow.invariant_id`. Pairing on the flow id alone calls that a migration and buries a functional change. Compare `config` before deciding |
| A test version assumed to pin its flow versions | it does not. `flow` carries `invariant_id` and nothing else, and the step schema rejects the `:N` suffix outright. Which flow version applies is resolved on read, so the pair to diff is inferred from `created_time` and the report says so |
| `get_mabl_test_steps` used to enumerate a test's flows | its `flows` array returned `flow_count: 1` on the test checked here, holding only the `structural` flow. Enumerate from the `EvaluateFlow` steps |
| `detail: "compact"` used to read flow references | compact drops `flow.invariant_id` entirely, leaving an `EvaluateFlow` with no `flow` key. Use the diff, or `detail: "full"` |
| The structural flow treated as a flow to expand | the test-level diff already **is** its steps, and its invariant id is not stable across a test's life. Expansion means the reusable flows the test calls |
| `list_mabl_flow_versions({ branch })` used to scope resolution | versions predating branching carry no `created_on_branch`, so the filter drops them along with the other-branch versions it was asked to drop — 11 versions down to 4 on one flow here — and says nothing about it. Resolve unfiltered and report the branch you landed on |
| `mabl tests export <id>:<N>` read as a version-scoped test **and** its flows | it is version-scoped for the test's own steps, and it inlines each nested flow, which looks like free expansion. The inlined flow bodies are the flows' **current latest**: a v72 export here carried flow text authored well after v72. Fine for the shape of a test at a version; never the basis of a flow comparison |
| `mabl tests export --mabl-branch` trusted to scope a read | three branch names from this test's own version history and one deliberately bogus name all produced files byte-identical to the unflagged export, with no error on the bogus name |
| A test disabled wholesale | invisible here — `compare` diffs steps only |
